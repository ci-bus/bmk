Logs

A firmware built with logs prints what it is doing on a USB serial port: start-up, Bluetooth connections, pairing and errors.

Enable logs

For a keyboard, add this line to its keyboard.h:

#define LOGS true

For the dongle, change the same line in app/src/dongle/dongle.h.

Then rebuild with a clean build folder, because logs add a USB serial device to the configuration:

west build -p always -b nrf52840 -- -DKEYBOARD=miguelio/mk60v1

Read the logs

Connect the keyboard with the USB cable. In addition to the keyboard, the computer now detects a serial port. Open it with any serial terminal, for example:

screen /dev/tty.usbmodem* 115200

On Linux the port is usually /dev/ttyACM0; on Windows it is a COM port that you can open with PuTTY.

Typical messages, each preceded by a timestamp and its level:

[BLE] MAC identity: E1:23:45:67:89:AB
BMK Keyboard started!
Advertising...
Connected...
Security changed L2 OK!
Pairing complete!

Logs travel over USB, so they are only visible with the cable connected. In that situation the keyboard sends its keys over USB and does not sleep, but Bluetooth keeps working and its connection messages are still printed.

Log level

The default level is the most detailed one. To print less, define LOG_LEVEL in keyboard.h with one of the Zephyr levels:

#define LOG_LEVEL LOG_LEVEL_INF
LevelPrints
LOG_LEVEL_ERRErrors only.
LOG_LEVEL_WRNErrors and warnings.
LOG_LEVEL_INFErrors, warnings and information.
LOG_LEVEL_DBGEverything. This is the default.

When you finish

Set LOGS back to false and rebuild with -p always. A firmware with logs exposes an extra USB serial device and is meant for debugging, not for daily use.

Crashes

If the firmware hits a fatal error, it restarts by itself instead of staying blocked. A keyboard that reconnects for no reason may be restarting; logs will show the start-up messages again when that happens.
